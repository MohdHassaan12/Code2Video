Concept Explorer · Design proposal

Studio: from a one-shot form to a scene-by-scene editor

Today the interface is a sidebar of thirteen knobs and one Generate button that runs the whole pipeline as a black box. This proposal reshapes it around the thing users actually want to touch — individual scenes — with modular editing of content, motion, and audio per scene, in the spirit of Google Flow's SceneBuilder and Descript's edit-the-transcript model.

Status ideation — nothing built yet Scope stem_animation_lab web UI + API Date 2026-07-30
TL;DR

The pitch in five lines

  • The storyboard IR is already a perfect editor document. Scenes → elements (content), animation events (motion), narration cues (audio), composition + layout template (style). The editor edits the IR; the deterministic transpiler keeps owning the code. No new codegen concepts needed.
  • The backend already has per-scene primitives the UI never exposes: per-scene scripts, parallel scene renders + ffmpeg concat, scene-scoped repair, and a shared TTS cache that makes re-renders of unchanged narration free. "Edit one slide, re-render one slide" is mostly wiring, not new machinery.
  • One surface, three views: a Library (today's /timeline, made openable), a Studio (scene rail + preview canvas + inspector with Content / Motion / Audio / Style tabs), and an Advanced drawer (absorbing the debug sandbox's repair history, code view, and cost readouts).
  • Every edit follows the house rule "never lose a verified artifact": edited scenes render as candidates, accept-if-better, old clip kept on failure.
  • Phase 0 is nearly free and pays immediately: the browser today never sends scene_scripts, so web renders always take the slow sequential path with no scene-scoped repair — one wiring fix turns the fast path on for everyone.
Diagnosis

Why the current interface feels confusing

This is grounded in the actual code (static/index.html, static/app.js, app/api/*), not vibes. The root problem: the UI is organized around the pipeline's stages, but the user thinks in scenes. Everything below follows from that mismatch.

One button, no pauses, no steering

Generate runs storyboard → preflight → codegen → compile as one unattended chain (app.js:330-492). You can't stop after the storyboard to fix a wrong cue, can't re-run codegen after a tweak, can't cancel.

The editable thing is the wrong thing

The storyboard renders in a read-only <code> block; the only editable intermediate in the whole UI is the Python textarea. Educators want to change a narration line or a label — instead they're offered Manim source.

All-or-nothing regeneration

Changing one word of narration means re-running the entire video. Meanwhile per-scene clips are rendered server-side — then deleted after concat (render.py:1166), with uuid names and no index, unreachable by design.

Four disconnected surfaces

Main page, /timeline, /bulk, and the Streamlit sandbox share no navigation and no state. Voice audition, repair history, env knobs, and cost readouts exist only in the sandbox; per-node regenerate exists only in the ce/ Streamlit app.

Progress is a log dump

2-second polling of a free-text progress string, then the entire Manim stdout dumped into a console pane at the end. The WebSocket push endpoint exists (render_routes.py:106) — no page uses it.

Fixes evaporate; state drifts

Asset re-tests patch the storyboard in browser memory only — there is no storyboard GET/PUT, so corrections die with the tab. Voice lists are hardcoded in app.js as a manual mirror of the sandbox's table. Server errors are silently dropped (client reads err.error, FastAPI sends detail).

The unlock

The backend is already scene-modular — only the UI isn't

This is why the redesign is cheaper than it looks. Each editor capability below maps to machinery that already exists and is tested; the missing layer is addressability (HTTP surface + persistence).

North star

The Studio: scene rail · canvas · inspector

One editing surface per project. The scene rail (bottom) is the film strip you flow through; the canvas previews the selected scene's clip; the inspector (right) edits the selected scene through four modular tabs. Everything on screen is a view of the storyboard IR.

Selection model in one sentence: the rail selects a scene, the canvas scrubs its cues, the inspector edits what's selected — and nothing ever edits generated code, because the transpiler owns structure.
Modular editing

Four tabs, each mapped 1:1 to IR fields

No invented concepts: every control below reads and writes an existing field of StoryboardScene. That keeps the editor honest — anything it can express, the deterministic pipeline can already render, and the existing storyboard gate can already validate.

The edit loop

Every edit is validated, scoped, and reversible

AI edits ride the same loop

An "Ask AI" box on the selected scene ("make this a two-step derivation", "add a real-world example element") sends the instruction + that scene's IR to the LLM and gets back a storyboard patch — never code. The UI shows the diff as chips (+2 elements ~1 cue scene 2 dirty) with Apply / Discard. Applied patches enter at step 1 like any manual edit, so gates and accept-if-better still protect the artifact. This keeps the house rule intact: models own content, code owns structure.

Information architecture

Three views replace four disconnected surfaces

Everything hangs off a persistent project (the generalized bulk_runs folder: storyboard, scene scripts, clips, final mp4, sidecar, cost — durable, resumable, sweep-exempt). One top nav: Library · Studio · Runs.

Where the sandbox goes

The Streamlit debugger's unique powers move into an Advanced drawer inside the Studio, opened per project: repair-round history with code diffs, per-stage cost and latency, generated code (read-mostly, with the escape-hatch recompile the sandbox has today), env-override knobs, raw sidecar JSON. Casual users never see it; the debugging workflow stops requiring a second app on another port. The sandbox itself can stay during migration — it shares the same API.

Creating a new video becomes a two-beat flow

Beat 1 — brief: topic + the few choices that shape the storyboard (persona, language, tech-terms, style), producing a storyboard in ~seconds for review in the Studio as an unrendered scene rail with blueprint thumbnails. Beat 2 — render: after skimming/fixing the scenes (this is where today's silent failures get caught for free), one button renders all scenes in parallel. The thirteen-knob sidebar dissolves: storyboard-shaping knobs into the brief, render knobs into Style, debug knobs into Advanced.

Two deliberate non-goals: no code-editing API beyond the existing escape hatch (structure stays code-owned), and no concurrent multi-user editing — env_overrides is process-global by design and this stays a single-author tool for now.

Rollout

Five phases, each independently shippable

P0Unblock what exists~a day

Forward scene_scripts from the browser's compile call (turns on the parallel path + scene-scoped repair for web users — today they always get the slow sequential path); read err.detail so server errors stop vanishing; add a shared nav header across / · /timeline · /bulk; serve voices from /api/voices. No redesign yet — pure wiring debt.

P1Glass box + project persistence~a week

Split Generate into brief → review → render; render the storyboard response as a read-only scene rail with blueprint thumbnails; project folders (keep clips, stop discarding); WebSocket per-scene progress; /timeline cards gain Open in Studio. The black box becomes inspectable before any editing ships.

P2Audio editing first~a week

The Audio tab: edit cue text, audition voices (/api/tts/preview), per-scene re-render with accept-if-better. Audio is the cheapest, highest-demand edit (the tech-terms knob exists because of a narration complaint) and exercises the whole PATCH → dirty → render loop on the least risky field.

P3Content + motion editing~1–2 weeks

Element list editing, entrance pickers, per-cue event chips, composition/layout-template controls; scene reorder / add / duplicate / delete on the rail (IR-level list operations + full re-concat).

P4AI edits + absorb the sandbox~a week each

Ask AI prompt-to-patch with diff preview; Advanced drawer (repair history, cost ledger readout when §H lands, code view, env knobs) so the Streamlit sandbox can retire from daily use.

Invariants

Rules the editor must never break

  • Never lose a verified artifact. Edits produce candidates; accept-if-better; losers discarded. An editor that can destroy a good video on a bad edit is worse than no editor.
  • Code owns structure, models own content. The editor and the AI box edit the IR only. The moment a UI control writes Python, the deterministic guarantees (probes, gates, repair) stop covering it.
  • Metered edges stay metered. Preview buttons and AI edits are LLM/TTS spends — show cost affordances (the cached · ₹0 chips), route through existing caches, and never put a metered call in a render-blocking hot path.
  • Validation before spend. Every PATCH runs the shape gate + language contract before any render; a rejected edit costs nothing and explains itself.
  • Long operations narrate progress per scene over the WebSocket — silence reads as a hang.
