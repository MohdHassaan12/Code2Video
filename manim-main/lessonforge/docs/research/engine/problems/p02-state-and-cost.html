Durable state, cost & run ledger

The one honest T1 on this site. It is here, ranked second, because every experiment the other nine problems need — A/Bs, bulk evals, cost-aware routing — is impossible to run rationally without it.
problems / 02
L · the loop doesn’t close T1 engineering — answer known Maturity: L1 — the repo’s own “biggest operational gap”
⚙️ Mechanics today
  • Jobs live in a bounded in-memory JobStore (app/jobs.py:27); a server restart forgets what was running. The only durable per-video record is the .mp4.json sidecar.
  • There is no cost tracking at all — no counter ties an LLM/TTS call to a job or a rupee pipeline-roadmap.md:594-596 — in a pipeline whose own measurement says TTS alone is ~85% of metered cost pipeline-roadmap.md:168.
  • The LLM edge has no wall-clock guard: call_gemini_with_fallback configures no timeout, and there is no stale-job detection, so a hung call leaves the job running forever pipeline-roadmap.md:494-501.
  • Artifacts scatter across temp_renders/, static/videos/, media_* — no per-run folder groups a video with its storyboard, scripts, logs and spend.
  • env_overrides repair knobs are process-global, last-writer-wins — explicitly a single-user debug affordance, not isolation CLAUDE.md:26-31.
🕳️ The gap — why it earns a page despite being T1

Nothing here is unsolved in the field — job stores, ledgers and timeouts are settled engineering. It earns a page because it compounds: P01’s eval loop needs per-run folders to compare runs; P04’s convergence study needs to know what a repair round costs; P07’s memory A/B needs stable run identity; and the roadmap’s own cost-ledger spec already names the two tests that make the ledger honest — “cached re-render is not free and unknown ≠ $0” pipeline-roadmap.md:597-607. The absence of this layer is why the strongest evidence in this audit had to be scraped from sidecars and directory counts instead of read from a ledger.

📎 Evidence
  • Stage H graded L1 — “⟵ biggest operational gap” pipeline-roadmap.md:581.
  • Measured oddity a ledger would have caught instantly: the shared TTS cache shipped 2026-07-19, yet .tts_cache/ at the repo root holds 0 entries (measured 2026-07-27) — either production renders since then never hit it, or the cache path diverges. Nobody can currently tell, which is precisely the problem.
  • The bulk runner writes resumable per-topic stage caches (bulk_runs/<run_id>/, bulk_runner.py:135) — the per-run-folder pattern exists in one corner of the codebase and nowhere else.
📚 Prior art

Settled practice: durable queues and job journals (any of SQLite-WAL job tables, jsonl journals), per-request cost metering at the client seam, and deadline propagation on outbound calls. Nothing needs a citation; it needs an afternoon.

🪜 Solution sketch — all $0, roadmap-endorsed
  1. $0 Wall-clock timeout + retry budget on the google-genai SDK call in app/llm.py; stale-job sweep in JobStore.
  2. $0 Durable jobs.json journal (the roadmap’s planned shape) so a crash answers “what was running.”
  3. $0 runs/<topic-hash>/ per-run folders — generalize the bulk runner’s existing cache layout to single renders.
  4. $0 Cost ledger at the two metered seams (app/llm.py, the TTS client in viz_helpers.py), pinned by the roadmap’s two named tests; surface per-video spend in the sidecar and on /timeline.
📏 How we’d measure it

After: kill -9 mid-render leaves no forever-running job (pin as a harness check, house style — LLM stubbed); every mp4 in static/videos/ traces to a run folder with a cost line; the .tts_cache/ anomaly above becomes answerable from the ledger in one query.
