The verifier sets the expressiveness ceiling

Camera zoom and pan are deliberately absent — not unbuilt, forbidden, because a moving camera would blind the probe. The general form: every visual capability is capped by the verifier’s assumptions, and verifiers that survive capability growth are an unsolved design problem.

⚙️ Mechanics today
  • The only camera verb is semantic: focus — dim everything except the target, then restore (viz_helpers.spotlight_on/off:1653/:1678, emitted by transpiler.py:1004-1010) — chosen precisely because “opacity changes geometry not at all, so every probe invariant survives” CLAUDE.md:166-173.
  • Zoom/pan via MovingCameraScene are barred: the probe’s clipped-text check measures against a fixed config.frame_width/height; a moving camera “would report legitimately off-frame content as clipped and miss real clipping — it would break the verifier” CLAUDE.md:166-173.
  • The generalized rule is already doctrine: “a rendering feature that invalidates a verifier must ship with the verifier upgrade, never before it” reference-architecture.md:1080-1082. The unblocking item is open roadmap priority #17, “Frame-aware probe” pipeline-roadmap.md:658.
🕳️ The gap — why this is research-grade

The camera is the visible symptom; the disease is coupling. The probe verifies by reading Manim’s internals — it patches Scene.play and measures mobject geometry against frame constants. That makes it exact, and makes it fragile in two directions: any capability that changes the geometry↔screen mapping (camera, 3D, scaling groups) silently invalidates it, and any new renderer backend (the §21 RendererBackend contract names SVG/web, Three.js, Blender, Unity) needs the whole probe family re-invented per backend. The open question: what does verification look like when it must survive capability growth — probe the projected geometry (frame-aware transforms), or probe the pixels (backend-independent but inheriting all of P03’s trust problems)? This is a capability the incumbent structurally cannot have without answering that question first.

📎 Evidence
  • The constraint is enforced socially today — a doc rule (“Implement camera moves only together with a frame-aware probe”) — with no test pinning it; nothing stops a future contributor from adding MovingCameraScene and quietly blinding the probe.
  • The cost is real pedagogy: the zoom-into-detail move is a staple of the 3Blue1Brown genre this system emulates; every storyboard that wants one gets a spotlight instead.
  • Precedent that the ceiling can move: the spotlight itself was implemented as the probe-safe subset — proof the team designs capabilities around the verifier (the discipline this page generalizes).
📚 Prior art citation-check before external use

Camera planning is a solved craft in graphics/cinematography literature (constraint-based virtual cinematography); that is not the hard part here. The hard part — verification oracles that survive system evolution — is the metamorphic testing problem: define properties invariant under the new capability (text legibility in view space, not world space) and check those. Compiler correctness work (translation validation) offers the cleanest analogy: verify the projected output of each transform, not the transform’s internals.

🪜 Solution sketch — cheap → deep
  1. $0 Pin the constraint: a harness check that fails if generated code ever contains MovingCameraScene while the probe is frame-fixed — turning a doc rule into a gate (the house pattern for every other trap).
  2. $0 Frame-aware probe v1: track the camera transform (center, scale) at each beat and map mobject bboxes into view space before the clipped/overlap checks — roadmap #17, no new dependencies, pinned by planting a clipped-text bug under zoom in test_overlap_probe.py style.
  3. metered Ship zoom/pan as Director directives only after v1 lands, with an A/B on the benchmark topics — does camera language reduce violations-adjusted quality or improve it (needs P01 to answer honestly)?
  4. research Backend-independent verification for the §21 multi-backend future: a probe contract stated in view-space/pixel-space properties that any RendererBackend can satisfy — converging with P03 if the answer is pixels.
📏 How we’d measure it

The verifier’s own standard: under zoom, a planted off-view clipped text must be caught and a legitimately off-frame element must not be flagged (the exact failure CLAUDE.md predicts). Then violation rates with camera moves enabled vs. disabled on the same boards — expressiveness gained per violation added.
