Self-improving repair memory is inert

The system fixes the same classes of failure over and over — and remembers none of it. A full error→fix memory is coded on both the write and read side, and it is switched off.

⚙️ Mechanics today
  • app/rag.py (125 lines) implements a ChromaDB store of error→repair pairs: _store_repair_pair is called from five sites in app/render.py; _retrieve_past_fixes feeds the repair prompt from app/codegen.py:172.
  • All of it is behind CHROMADB_ENABLED, default off (rag.py:17 early-returns; both collections stay None) — so retrieval returns [] and storage no-ops in every default render.
  • Independently, the read side (“pre-patching a known failure before its first render”) “was dropped in a merge except for the LaTeX path” reference-architecture.md:903-908 — the roadmap calls this the only substantive gap left in stage F (gap F3 pipeline-roadmap.md:444-447).
  • The error-fingerprint/resolution index — the thing that would make failures addressable — is the explicitly named reason stage F “is not L3+” pipeline-roadmap.md:400-403.
🕳️ The gap — why this is research-grade

The engineering exists; what’s unsolved is whether and how memory actually helps. Three open questions, in rising order of difficulty: (1) Fingerprinting — when are two render failures “the same problem”? Tracebacks vary by line number, scene id, topic; a fingerprint that’s too tight never matches again, too loose retrieves poison. (2) Yield — does retrieval-augmented repair measurably cut rounds-to-converge? Never measured here, and field results on retrieval-for-repair are mixed. (3) Poisoning — a stored “fix” that merely passed accept-if-better once can be wrong in general; memory that learns from its own outputs can entrench a bad pattern. The house rule “never lose a verified artifact” has no analog yet for verified knowledge.

📎 Evidence
  • Measured: chroma_db/ exists on disk; the flag keeps it empty of new pairs in default runs.
  • Measured: 185 trace_*.json files in debug_sandbox/debug_traces/ — full generation traces, the richest failure corpus in the repo, mined by nothing.
  • The recurrence it would attack is documented: the overlap fix-of-fix chain (P04), and the repeated “selective import satisfies the guard” trap that bit twice CLAUDE.md:110-137 — same lesson, re-learned.
📚 Prior art citation-check before external use

Crash dedup/grouping is production-proven (Sentry-style stack fingerprinting) and directly applicable to render failures. Case-based and retrieval-augmented program repair is an active research line with positive-but-noisy results. Experience replay with verification-before-storage is the standard defense against self-poisoning; “only store what stayed correct” as a memory admission gate mirrors this repo’s accept-if-better and is a natural, publishable extension of it.

🪜 Solution sketch — cheap → deep
  1. $0 Flip CHROMADB_ENABLED=1 on a branch and replay the harness + the three benchmark topics; measure retrieval hit-rate and repair rounds with memory on vs. off. (An A/B this cheap not having been run is itself the maturity finding.)
  2. $0 Mine the 185 debug traces into a fingerprint corpus: cluster failures, count recurrences — this decides whether memory is worth the complexity before any new code.
  3. metered Restore read-side pre-patching beyond LaTeX (the F3 gap), behind the same accept-if-better guard: a pre-patch is kept only if the render passes.
  4. research Verified memory: admission (store only fixes that survived N later runs), decay (evict fingerprints that stop matching), and provenance (every retrieved fix names the incident that taught it — the CLAUDE.md “record it WITH what taught it” rule, mechanized).
📏 How we’d measure it

Primary: rounds-to-converge and repair spend with memory on/off across a bulk suite (shares P04’s metric and needs P02’s ledger). Guard metric: retrieval precision — a retrieved fix must be rated relevant for the failure it was offered on; poison events (a retrieved fix that made things worse) must be counted, not just losses discarded.
